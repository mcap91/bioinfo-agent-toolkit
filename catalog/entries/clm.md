## What it does

CLM (Contrastive Language Models) is a "System One" classification model from Stanford/Hazy Research and NVIDIA Research, released as an open-weights, self-hostable alternative to TypeSafe AI's Jev (see `jev` entry). It implements the same three typed-question primitives as Jev — Choice (categorical probability over options), Noul (true/false probability), and Score (rubric/ordinal scoring) — and its client library (`clm`) accepts Jev's wire format directly: "a request written for TypeSafe replays as `client.system_one(state, questions)`."

Architecture: a frozen Qwen3-8B backbone produces last-token-pooled embeddings; a state encoder and an action encoder are each the frozen backbone plus a separate ~20M-parameter trainable projection head. The two heads are trained with a bidirectional InfoNCE contrastive loss so a state embedding is pulled toward the action actually taken and pushed away from other candidates. At inference, CLM scores each candidate action by the dot product of its embedding with the state embedding; a softmax over those scores is the answer distribution. Because state and action embeddings are computed independently, action embeddings can be cached and reused across requests ("disaggregated caching").

Training recipe (three stages): pre-training on ~60M Nemotron DQA question-answer pairs; mid-training on ~30M synthetic hard negatives generated by Gemini 2.5 Flash-Lite; post-training on ~1M agentic trajectories (Agent Data Protocol, Endless-Terminals, LiteCoder-Terminal-SFT). The reference release, `Contrastive-LM/CLM-v0.1-8B`, is a ~75MB checkpoint (`torch.save` dict with `state_head`/`action_head` state dicts, `logit_scale`, and architecture `cfg`); any head in that checkpoint format is only meaningful paired with the Qwen3-8B encoder and pooling it was trained against.

## Serving and API

Deployment is two processes: a vLLM pooling-mode server for Qwen3-8B embeddings (`vllm serve Qwen/Qwen3-8B --runner pooling --max-model-len 2048 --port 8090`) and `clm-serve` (FastAPI, port 8700 by default), which downloads the reference head on first run and also serves a web playground at `/`. Endpoints: `POST /v1/systemone` (Jev-compatible typed-question endpoint), `POST /v1/rank` (rank free-form candidates against a context/question), `GET /v1/models`, `GET /health`. Python usage mirrors Jev's client: `from clm import CLMClient, Choice, Noul, Score`, or the in-process `Engine` class (`engine.rank(...)`, `engine.answer(...)`) for use without a server. Default state length is 2048 tokens (truncated beyond that); longer states require raising `--max-model-len` on the vLLM server and `clm-serve --max-tokens` together (more GPU memory).

Performance claims from the repo: zero-shot, CLM-8B performs on par with Jev on computer-use, gaming, and tool-calling benchmarks while running up to 9x faster (e.g., T-Rex: 16.5ms vs Jev's 149.8ms; BFCL v4: 95.2% vs Jev's 99.2%; WikiRacing: 26/30 vs Jev's 30/30 — CLM trails slightly on the latter two). With lightweight fine-tuning as a verifier, CLM reaches new SOTA on held-out DeepSWE (81.6%) and Terminal-Bench 2.1 (87.6%) while running 4.1-5.7x faster than Jev; the repo states Jev scores below pass@1 as a verifier on these long-horizon agentic tasks. A reserved on-device vector cache (`--action-cache`, LRU eviction) skips the encoder call entirely on revisited states, reported at roughly 2.8x additional speedup for loops that re-visit states.

## Requirements and licensing

Linux, Python 3.10+, and an NVIDIA GPU for the Qwen3-8B encoder (the heads alone can run on CPU). `pip install contrastive-lm`, or `pip install -e .` from a clone. Code and the CLM-8B weights are both Apache-2.0.

## Where it differs from Jev (per source material and repo)

CLM wins on latency (4-13x depending on workload, driven by disaggregated state/action caching), openness (downloadable ~75MB heads that can be fine-tuned on custom data via `train/finetune.py`), and verifier accuracy on the two agentic benchmarks reported above. Jev leads on zero-shot broad knowledge (larger proprietary backbone), context length (64K for Jev vs. CLM's default 2K, extensible to ~8K+ with more GPU memory), and absolute probability calibration — CLM's probabilities are relative to the candidate set given in a request rather than an absolute, generative-model calibration.

## Security

Apache-2.0, fully self-hostable — no third-party API dependency (unlike Jev, which requires a `TYPESAFE_API_KEY` against TypeSafe's hosted service). `clm-serve` supports an optional `CLM_API_KEY` bearer-token requirement; CORS is off by default specifically because, per the repo's own docs, an API key would otherwise "travel in a header any page would then be free to send" if cross-origin requests were allowed. Requires standing up a GPU-backed vLLM server, which is additional self-hosted attack surface compared to Jev's fully managed API.
